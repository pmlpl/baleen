# `eval/queries/` — 检索评测的 20 条 query

> **一句话**：20 条 query 全部从**库里真实存在的笔记**出题，`expected_heading_path` 逐条回查过数据库
> 父块表才写下的。**相关性判定全部由本代理（DSH-评测）自判，没有人工标注，必须复核。**

---

## 1. 这些 query 是怎么来的

### 1.1 先查库，不够就先导入真实笔记

开工时库里只有 **3 篇**，而且都是早期为验证导入管道造的**假数据**，不是真实笔记：

| note_id | 标题 | 性质 |
|---|---|---|
| 10 | 导入冒烟笔记 | 合成，一段闭包示例 |
| 27 | 解析选型测试(Markdown) | 合成，专门测 markdown-it 的各种块 |
| 70 | Git Bash 常用命令备忘 | 合成，两条 git 命令 |

3 篇 < 5 篇，按任务书用 `backend/scripts/import_smoke.py --no-llm --file` 从 `eval/samples/_inbox/`
**只读导入**了 8 份真实笔记（**没有复制、没有改名、没有移动样本文件**）：

| 导入后的 note_id | 标题 | 父块 |
|---|---|---|
| 156 | 闭包 —— 面试必问，装逼必备 | 20 |
| 157 | Fetch / Axios 完全指南 | 23 |
| 158 | 手写实战练习 —— 面试手撕题全集 | 34 |
| 159 | 变更 016：5 个核心工具补单测（file_tool / registry / script_tool / mcp_capture / crawl_tool） | 19 |
| 160 | 缺陷反馈：VIP音乐播放能力缺失（最终版） | 11 |
| 161 | Agent 应用开发学习指南 | 48 |
| 162 | 项目实验实训报告（一） | 7 |
| 164 | 轻量化发票 OCR 识别与校验系统 | 15 |

合计 **11 篇笔记 / 184 个父块**（另含 3 篇冒烟假数据的 7 个父块），子块 309 个（300 字档）。

> 那 3 篇假数据**没有拿来出题** —— 它们是为验证管道造的，不代表任何真实使用场景。

### 1.2 出题时守着两条纪律

1. **期望值必须能回查**：写 `expected_note_title` / `expected_heading_path` 之前，先跑
   `select note_id, heading_path from chunks where is_parent ...` 把父块面包屑抄下来，
   再用 `select ... where text like '%术语%'` 确认那个术语确实落在那个父块里。
   `ablation.py` 里还有一道 `check_expected_paths()` 自检：任何一条期望路径在库里找不到就**直接报错退出**，
   不会算出一条假的"没命中"。
2. **术语类必须原样出现**：5 条 `term` 的 query 里都含有笔记正文里的原字符串，逐条对应见 §3。

## 2. 列说明（CSV 8 列）

| 列 | 含义 |
|---|---|
| `qid` | `q01`–`q20` |
| `query` | 就是投给（将来的）`POST /api/search` 的原话 |
| `intent` | 这一问用户到底想找什么（中文短语，给人看的） |
| `expected_note_title` | 期望命中的笔记标题；**`NA` = 负例，库里不该有** |
| `expected_heading_path` | 期望命中的父块面包屑。**多条用 ` \|\| ` 分隔** = 命中任一条即可（跨节综合的 query 才有两条） |
| `difficulty` | `easy` / `medium` / `hard`，本代理自评 |
| `kind` | 六类，见 §3 |
| `note` | 来源与复核标记：`来源=库内笔记#id` + 相关性是否自判 |

## 3. 六类 `kind` 怎么分类

任务书要求 20 条构成：术语 5 / 同义 5 / 跨节 3 / 长查询 3 / 短查询 2 / 负例 2。

| kind | 条数 | 判定标准 | 考的是哪条路 |
|---|---|---|---|
| `term` | 5 | query 里**原样出现**笔记正文中的专有名词 / 型号 / 错误码 / 函数名 | 词法路（trgm 精确重叠） |
| `paraphrase` | 5 | 用日常说法问同一件事，**刻意避开原文的专有名词**（如问闭包成因时不写"闭包"，问 token 刷新时不写"拦截器""401"） | 向量路（考语义而不是字面） |
| `cross-section` | 3 | 答案**分散在同一篇笔记的两个小节**里，`expected_heading_path` 写两条 | 两路都要（子块粒度够细才拼得起来） |
| `long` | 3 | **≥ 30 字**，像真人提问那样带背景、带约束 | 长 query 的语义稀释问题 |
| `short` | 2 | **≤ 6 字**（`内存泄漏排查` = 6、`深拷贝` = 3） | 极短 query 的信息量不足问题 |
| `negative` | 2 | 库里确实没有 → `expected_*` 填 `NA` | 不该命中的时候能不能不硬凑 |

## 4. ⚠️ 哪几条的相关性是本代理自判、需要主人复核

**诚实交代：20 条全部是我（本代理）自判的，没有一条是人标的。**
按「我有多确定」排个序，**建议按下面顺序复核**：

| 优先级 | qid | 为什么我拿不准 |
|---|---|---|
| **1（最该复核）** | q11 / q12 / q13（`cross-section`） | 一条 query 有两个期望父块。**"这两节是不是真的都算答案"完全是我的判断** —— 少写一节会让 Recall 虚高，多写一节会让它虚低 |
| **2** | q14 / q15 / q16（`long`） | 长 query 里夹了多个关注点（q14 同时问"顺序"和"要留哪些文件"），期望父块只锚住了其中一节。若认为该锚另一节，命中名次会整体变化 |
| **3** | q06–q10（`paraphrase`） | 改写幅度是我定的。"改写得多远"直接决定它考的是向量路还是词法兜底。q09 / q17 我还**刻意从严**：只认 4.2 一节，4.1 / 4.3 明明也相关但判为不命中 |
| **4** | q01–q05（`term`） | 最确定：术语原样在正文、父块面包屑直接抄自数据库。复核成本最低，建议只抽查 |
| **5（最省事）** | q17 / q18（`short`）、q19 / q20（`negative`） | 短查询只看答案位置；负例只看"库里真没有"，grep 一遍就能确认 |

**两条负例的确认方式**（可复核）：

- q19 `MySQL 的间隙锁…`：库里只有 SQLite 与 SQLAlchemy 的提及，**没有任何 MySQL 间隙锁 / 隔离级别的内容**。
- q20 `红烧肉…`：库内全是软件工程与前端技术笔记，与烹饪无关。

> 负例在**纯向量检索里永远召不满空集**（总能返回 top-k 最近邻）。所以 `ablation.py` 不把负例算进
> Recall / MRR，只单独报"top1 相似度"并与正例的 top1 均值对比 —— 详见 `eval/ablation.md` §3。

## 5. 命中口径（与 `eval/scripts/ablation.py` 完全一致）

一条 query 在名次 `r` 上**算命中**，当且仅当：

1. 该名次上的**父块**所属笔记标题 == `expected_note_title`（多条 `||` 时任意一条）；
2. **且** 该父块的 `heading_path` 与 `expected_heading_path` 能对上 —— 口径是
   「**去空白后完全相等，或一方是另一方的严格面包屑前缀**（`x > y` 与 `x`）」。
   `x > y` 与 `x > z` 这种**同级的兄弟小节不算对上**。

三条硬约定：

- **父块级评分**，不是子块级。子块命中后一律按 small-to-big 折成父块再排名（同一父块的多个子块只占一个名次）。
- **口径从严**：宁可漏判不虚高。q09 / q17 的相邻小节本也相关，但按单路径口径判为不命中。
- `NA`（负例）不参与 Recall / MRR 分母。

## 6. 与 `eval/TASK.md` D6 的差异

TASK.md D6 预告的 schema 是 `queries.json` + `relevant: [rel_path...]`（按**文件**给相关性）。
这里落地成 CSV 且精确到 **heading_path**，原因：

- 本项目的命中单位就是**父块**（`docs/api.md` §4：响应 `hits[]` 是父块），按文件给相关性测不出
  「同一篇笔记里找对了哪一节」；
- 多一列 `kind`，才能做 `eval/ablation.md` 里那张**按 kind 分项**的表（答辩要拿它说明
  "切块参数对哪类 query 敏感"）。

TASK.md 没被修改（只读）。
