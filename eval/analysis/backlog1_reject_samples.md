# backlog #1：补驳回样本（现状与待办）

> 立项来源：`eval/analysis/backlog_plan.md` ④。触发点：2026-11-19 分源 ok 率首跑发现
> **问答导出档 0 条 reject 样本**——那一档的 0% 误拒率只证明「不过度丢弃」，没证明「不过度接收」。

## 一、现状（2026-11-19 实测）

| 来源 | accept | partial | reject | 评价 |
|---|---|---|---|---|
| 文档（老金标准）| 17 | 1 | 18 | ✅ reject 充足 |
| 文档导入 | 3 | 0 | 0 | ⚠️ 无 reject |
| 视频转写 | 16 | 1 | **3** | ⚠️ 偏少 |
| 问答导出 | 12 | 0 | **0** | ❌ **完全没有** |

## 二、硬约束：问答导出的 reject 样本不能凭空造

问答导出内容是 AI 整理用户对话产生的，**天生质量不会太差**——真正该拒的是「问一堆废话存成笔记」那种。

**造出来的样本是假样本**，会污染评测集（违反「评测集质量 = 抓没抓到真问题」的纪律）。
所以这一档只能**在真实使用中等它发生**：

1. 主人日常问答时，如果某次存笔记的内容其实没价值（纯闲聊/纯情绪/纯重复），
   **不要立刻删**——它已经被 `eval_capture` 自动归档进 `eval/inputs/candidates/`
2. 隔段时间跑 `find_reject_candidates.py`，看有没有新的低分候选
3. 人工确认「确实该拒」后转正

## 三、我做了什么

**工具**：`eval/scripts/find_reject_candidates.py` —— 从现有候选池里**筛**（不是造）：
- 判据：机器 G2 判 reject/junk（最强）+ 正文短（<800 字）+ 营销/无信息关键词 + parse_status != ok
- 输出：按分数排序的候选清单 + 命中理由
- **只出候选，不做裁决**——转正权在主人

**首跑结果（2026-11-19）**：6 条候选，其中**2 条高价值**（各 9~10 分，机器判 reject/junk，且**未转正**）：

| 候选 | 机器判定 | 为什么该拒（人工复核结论） |
|---|---|---|
| `499aec4b58eb_「Github一周热点137期」快速看懂 DeepSeek superAgent.md` | reject / junk | ① 后段完全跑题（讲新疆旅游花费）② 前段只是项目名+链接罗列，没有实质知识 |
| `42b651897cb4_「Github一周热点137期」快速看懂 DeepSeek superAgent.md` | reject / junk | 同上（同视频的另一次捕获，21KB vs 26KB） |

⚠️ **但它们都是「视频转写」来源，不是问答导出**。转正它们只能把视频档从 3→5，**补不了问答导出档**。

### ⚠️ 这里有一个需要主人裁决的标注分歧

同一个视频（GitHub 周报 137 期）在库里出现了**三个版本**：

| 归档 | 机器判定 | 人工标签 | 说明 |
|---|---|---|---|
| `95f379a65451`（已转正）| accept / normal | **accept / normal** | 转正时标了「来源=文档导入」，理由「含可直接复用的知识单元」 |
| `499aec4b58eb`（未转正，26KB）| **reject / junk** | — | 后段跑题（新疆旅游） |
| `42b651897cb4`（未转正，21KB）| **reject / junk** | — | 同上 |

**分歧点**：同一个视频的三个转写版本，人工说其中一个「有可复用知识」，机器说另两个「junk」。
可能性有三种，需要主人看内容定：
- (a) 三个版本内容确实不同（转写质量/完整度不同）→ 各自独立判，都对
- (b) 内容基本相同，人工那次判宽了 → 应改 accept → reject
- (c) 内容基本相同，机器判严了 → 两条新候选该 accept

**我的观察（仅供主人参考）**：我抽看 26KB 和 21KB 两版的头部，前段都是「项目名 + GitHub 链接」的罗列，
后段 21KB 版明确出现「去新疆要花多少钱」这类跑题内容。倾向于 (a) 或 (b)，但**不替主人定**。

## 四、需要主人做的两件事

### ① 决定这 2 条要不要转正（视频档 3→5）

同源已经有一条转正且标 reject（`95f379a65451_「Github一周热点137期」…`，注意那条是 accept/normal——machine 判 accept 但人工标 reject；这两条是 machine 判 reject）。

转正步骤（如果主人同意）：
1. 把文件从 `eval/inputs/candidates/` 挪到 `eval/inputs/samples/_inbox/`
2. 在 `eval/inputs/labels.csv` 追加两行（`human_verdict=reject`, `human_quality=junk`, `human_next_action=drop`，reason 写清「视频后段跑题+前段仅项目罗列」）
3. 重跑 `metrics.py --split all --ok-only` 看分源数字

### ② 问答导出档的 reject 样本只能等真实使用

**建议**：主人平时用问答存笔记时，如果发现某篇「其实没什么价值」，别急着删——
先留一两天，让它进候选池。累积到 3~5 条后跑 `find_reject_candidates.py`，
人工确认后一起转正。这样那一档才有真正的「该拒的拒没拒」考核面。

## 五、为什么这一项我不擅自做

**评测标签纪律**：转正 = 修改金标准 = 改变论文里所有数字的分母。
2026-11-18 那次批量转正就出过一条错（`087efedeca46` 自述测试笔记被标成 accept/core，
2026-11-19 才发现并改判）。**同样的错不能再犯第二次**——所以我只出候选清单和证据，
不替主人做裁决。

## 七、写完这份文档的一个附带发现

候选池里有**重复捕获**：同一视频（GitHub 周报 137 期）被捕获了 3 次（`499aec4b58eb` 26KB /
`42b651897cb4` 21KB / `95f379a65451` 已转正）。原因是不同时刻/不同模式导入同一视频产生了
不同 sha 的转写文本。**这不是 bug**（视频转写内容确实会变），但转正时要挑一次，别把
同源三条都塞进金标准——那会让「视频转写」这一档的权重被人为放大。
