## 0. 一条铁律

**判「有没有可复用的知识」，不判「属于哪个学科」。**

- 一份写得很好的《软件工程》复习笔记 → accept
- 一份同属计算机领域、只有 20 行 `Traceback` 的日志 → reject
- 一份**课程无关**但记录了可复现踩坑过程的笔记 → accept（它换个人也能用）

判定问句固定为三句，按顺序问：

1. **这份文件里有没有一句话/一段结论，是作者以外的人能直接拿去用的？**
2. **拿走作者本人（他记得的上下文），这段内容还站得住吗？**
3. **换一台机器、换一个项目，它还能复现/复用吗？**

三问全否 → `reject`；第 1 问是、2/3 部分否 → `partial`；三问全过 → `accept`。

### 0.1 前置问：这是"复述规则"还是"自己想明白的"？

三问之前先看文件的性质——**写得详细 ≠ 有知识**。

| 文件性质 | 典型特征 | 倾向 |
|---|---|---|
| **复述别人定的规则 / 执行流程** | 按模板填的过程记录、任务汇报、制度复述、验收标准罗列 | **`reject`**，哪怕写得再细、换个人确实能照着做 |
| **记录自己想明白的东西** | 踩坑后的原因分析、"为什么这么选"、可复现的问题与修复 | `accept`，这才是知识 |

判据一句话：**这句话是在"汇报我做了什么"，还是在"告诉别人为什么这么做"？**

**已确认的对照案例（同一件事的两份文档，判定相反）**：

| 文件 | 写了什么 | 判定 |
|---|---|---|
| `项目实施记录（一）.md` | 环境搭建 + Git 规范，逐条汇报"做了什么" | **`reject`** / junk |
| `项目实验实训报告（一）.md` | 同一件事，但写了「问题—原因—解决」（RapidOCR 在 3.13 装不上→锁 1.2.3；opencv 冲突→`--no-deps`；CRLF/LF→`.gitattributes`） | **`accept`** / core / case |

> 这两条是同一门课、同一次实训的产物。**知识不在事有多大，在有没有把"为什么"留下来。**

## 1. charter 条目 ↔ 判据对照

写 rubric 时不能凭"感觉像笔记"，要能对回 charter 的每一条。

| charter 原句 | 落到哪类文件 | 默认判定 | 默认质量 |
|---|---|---|---|
| 收：需求与设计文档 | SRS、概要/详细设计、接口契约、架构说明 | accept | core |
| 收：测试计划与缺陷记录 | 测试计划、用例表、缺陷单（含现象/根因/修复） | accept | core |
| 收：项目过程记录 | 周报（**有实际进展**）、评审记录、度量表、里程碑记录 | accept | normal |
| 收：技术笔记与论文摘要 | 自写笔记、学习总结、论文/技术文章整理 | accept | core / normal / reference |
| 收：可复现的问题记录 | bug 复盘、环境配置踩坑、性能排查记录 | accept | core |
| 不收：无上下文的报错堆栈 | 只有 Traceback / 日志片段，无触发条件、无结论 | reject | junk |
| 不收：纯模板无信息量的周报 | 只填了姓名/日期/部门，正文是模板占位句 | reject | junk |
| 不收：聊天记录 | 微信/QQ/群导出，纯寒暄或只有过程无结论 | reject | junk |
| 不收：下载的发票/说明书 | 与个人知识库无关的外部单据、产品手册 | reject | junk |
| 不收：纯截图 | 未加任何文字说明的屏幕截图、表情包、壁纸 | reject | junk |

> ⚠️ 表里是**默认**，不是自动结论。命中默认值也要在 `human_reason` 写一句为什么。

## 2. 三档判定（accept / partial / reject）

### 2.1 判据

| 判定 | 判据（满足即成立） | 反例（**不算**这一档） |
|---|---|---|
| `accept` | 主体内容可被独立复用：有结论、有步骤或可直接引用的知识单元；噪声（页眉页脚、水印、目录）不影响理解 | 只有标题的 md；只有一段报错的 txt；100 页课件里 3 页有用、其余是封面和目录（→ partial） |
| `partial` | 文件里**存在**真实可复用内容，但占比小、位置局部，或需剔除大量噪声才能用；**必须**填 `human_valued_span` | 整篇都是模板的周报（→ reject）；整篇都是闲聊的群聊（→ reject）；疑似有用但读不懂（→ 先按可读性判，见 §5.3） |
| `reject` | 读完之后，**没有任何一句**能被下一个人复用；或内容与 charter 的"不收"清单直接对应 | 扫描件因为没文本层就判 reject（**典型误拒**）；英文论文因为不懂就判 reject；文件很大就判 reject |

### 2.2 落到具体文件类的反例（"不算"清单）

- **长 ≠ 有价值**：400 页课件 PDF 里只有 5 页讲清了一个流程 → `partial`，不是 `accept`。
- **专业 ≠ 有价值**：一份全是术语堆砌、没有解释、没有例子的"复习提纲" → 不因为难读就 `accept`，按是否有可复用知识判，通常 `reject`，理由写"术语罗列，无解释与例子"。
- **短 ≠ 没价值**：3 行但写清"这个报错是因为 X，改成 Y 即可"的 txt → `accept`（`core`）。长度不是判据。
- **文件名 ≠ 内容**：叫"论文.pdf"实为发票 → 按**内容**判 `reject`，`human_reason` 必须写明"文件名误导"。
- **格式 ≠ 内容**：`.docx` 里贴了一张截图，没有任何说明文字 → `reject`（纯截图），不是 `accept`。
- **重复 ≠ 新知识**：与库内另一文件 sha256 相同 → 见 §5.4。

### 2.3 边界模糊时怎么办（单用户策略）

默收 + 标质量（`AGENTS.md` 决策 9）。三问里 1 是、2/3 说不清时：

- 选 `partial` 而不是 `reject`，并把不确定点写进 `human_reason`；
- 选 `reject` 只在能明确说出"读完没有任何可复用内容"时。
- **误拒代价 ≫ 误收代价**，所以 `reject` 的理由必须具体到"缺什么"，不能写"质量低"。

## 3. 质量四级（core / normal / reference / junk）

质量与判定**正交**：`reference` 可以是 `accept`；`junk` 几乎总是 `reject`；`partial` 的质量通常是 `normal` 或 `reference`。

| 等级 | 定义 | 具体例子（3 个） |
|---|---|---|
| `core` | 一手知识，可直接当作答案来源；结论明确、上下文自足 | ① 带「现象 / 复现步骤 / 根因 / 修复」的 bug 记录；② 自写的闭包笔记（定义 + 反例 + 可运行示例）；③ 含前置条件与预期结果的测试用例表 |
| `normal` | 有真实信息，但需要整理、摘录或补上下文才能用 | ① 带页眉页脚水印的课程课件，知识点完整；② 有具体决议和待办的评审/会议记录；③ 写了实际完成项与卡点的实习周报 |
| `reference` | 事实性/查阅型资料：用来**查证**而不是用来**理解** | ① 双栏论文 PDF（可引用其方法/结论）；② 项目的 README / CONTRIBUTING / 部署说明；③ 课程大纲、术语表、参数对照表 |
| `junk` | 没有可用信息，或信息无法脱离原始上下文 | ① 只填了姓名和日期的模板周报；② 一段无触发条件、无结论的 Traceback；③ `hello.txt` / 空文件 / 3 行占位 txt |

判定与质量的常见组合（供对照，不是硬规则）：

```
accept  + core      ← 最想要的一类
accept  + normal    ← 课件、过程记录
accept  + reference ← 论文、README、大纲
partial + normal    ← 大文件里局部有用
partial + reference ← 表格/附录里只有几行有用
reject  + junk      ← 模板、纯截图、重复件、空壳
```

> 出现 `accept + junk` 或 `reject + core`，一定是哪里判错了，回头重看 §2。

## 4. 14 个槽位：该槽的标注要点

槽位编号填在 `labels.csv` 的 `slot` 列（人填，脚本留空）。一个文件可落在多个槽的语义区间，取**主**失败模式。

| # | 槽位 | 预期判定 / 质量 | 标注时最该盯的点 |
|---|---|---|---|
| 1 | 结构良好的自写笔记 | accept / core | 标题层级是否真能还原结构；代码块是否被抽成连续行 |
| 2 | 课程大纲 / 课件 PDF | accept / normal | 页眉页脚、水印、页码是否混进正文；目录页是否被当正文 |
| 3 | 论文 PDF（双栏、公式、参考文献） | accept / reference | 双栏串行是否错乱；公式是否退化成乱码；参考文献是否被当正文 |
| 4 | 测试用例表 / 测试计划 | accept / core | 表格行列是否对齐；合并单元格是否错位 |
| 5 | 需求规格说明书 SRS | accept / core | 多级编号（1.2.3）是否保留；需求条目是否被拆散 |
| 6 | 代码 README / 部署文档 | accept / reference | 命令块是否可复制；路径与版本号是否完整 |
| 7 | 扫描件 / 拍照笔记 | accept 或 partial | **先看图再判**；OCR 可读比例；不许因 `char_count` 低就 reject |
| 8 | 纯模板周报 | reject / junk | 正文是否有非模板句；只填日期姓名 → junk |
| 9 | 无上下文的报错堆栈 | reject / junk | 是否只有 Traceback；有无触发条件/结论（见 §5.1） |
| 10 | 带复现步骤的 bug 记录 | accept / core | 现象 / 根因 / 修复三要素是否齐全（与槽 9 成对） |
| 11 | 随手截图 / 表情包 | reject / junk | 有无文字说明；截图里是否含关键信息但无转录 |
| 12 | 重复文件（同名不同名） | reject / junk | 以 `dupe_of` 为准（见 §5.4） |
| 13 | hello world / 空文件 / 3 行 txt | reject / junk | 是否真空；有无一句可复用结论 |
| 14 | 文件名误导 | 按内容判 | 文件名只作参考，**一律以内容为准** |

`--random 10 --seed 42` 抽出的"日常平庸文件"不占槽位，`slot` 留空，照常判 —— 它们才是真实分布。

## 5. 六个边界情况的裁定规则

### 5.1 报错日志：什么算笔记，什么算垃圾

按四问打分（各 1 分）：

| 问 | 是 | 否 |
|---|---|---|
| ① 能定位到具体出错位置（文件/函数/行）吗？ | +1 | 0 |
| ② 写了触发条件或复现步骤吗？ | +1 | 0 |
| ③ 写了原因分析（哪怕未完全验证）吗？ | +1 | 0 |
| ④ 写了解决办法或"已验证修复"吗？ | +1 | 0 |

- **4 分** → `accept` / `core`（这就是槽 10）
- **2–3 分** → `partial` / `normal`；`human_valued_span` 标出"原因/修复"所在行
- **0–1 分** → `reject` / `junk`（这就是槽 9）

例外：单行报错但**指明了确定的修复动作**（"`xxx` 版本不兼容，锁到 1.2 即可"）→ 直接 `accept`，长度不影响。
反例（**不要**判 accept）：框架默认的错误页、只截了最后一行 `Error`、无任何上下文的一段 stderr。

### 5.2 聊天记录导出：有结论 vs 纯闲聊

- **有结论**（决策、方案对比后的选择、排障结论）→ `accept`（结论集中）或 `partial`（结论夹在几百条寒暄里），`note_type = chat`，`valued_span` 标出结论段落。
- **只有过程没有结论**（讨论热烈但无定论）→ `partial` / `normal`，理由写"有排查过程，无结论"。
- **纯闲聊 / 表情 / 复读** → `reject` / `junk`。
- 判据：**能不能从这段对话里摘出 1 句"以后照着做"的话**。能 → 至少 `partial`；不能 → `reject`。
- 注意：聊天记录里的**代码片段**若可独立运行，按代码内容判，不因载体是聊天就降级。

### 5.3 扫描件 / 拍照笔记：OCR 质量差时怎么判

`candidates.csv` 的 `ocr_needed = true` 只说明"没有文本层"，**不是判定**。人的流程：

1. 先打开文件看图（或渲染页），评估**主体内容可读比例**；
2. ≥ 80% 可读 → 按内容正常判（`accept` / `partial`）；
3. 30%–80% 可读 → `partial`，`human_valued_span` 写清"p3–p5 可读"；
4. < 30% 可读（模糊、过曝、手写难辨）→ `reject` / `junk`，`human_reason` 必须写"OCR/图像不可读，内容无法确认"，**不许**写"没有价值"。

硬规则：**`char_count = -1` 或 `ocr_needed = true` 绝不能单独作为 reject 的理由。**
反向也成立：图片清晰但内容是壁纸/表情包 → `reject`（与可读性无关，是内容与 charter 不符）。

### 5.4 重复文件：内容相同、名字不同

- 以 `candidates.csv` 的 `dupe_of` 为准（sha256 相同）。
- `dupe_of` **有值**的行 → `reject` / `junk`，`human_reason` 写"与 `<canonical rel_path>` 内容相同（sha256），属重复件"。
- `dupe_of` **为空**且是组内第一个的行（canonical）→ 按内容正常判，并在 `human_reason` 注明"库内另有 N 份副本"。
- **近似重复**（改了标题、增删一段，sha256 不同）→ 不按重复件处理，按内容判；理由里注明"近似重复于 X"，供后续去重策略参考。
- 注意：内容相同但**文件名不同**这件事本身是槽 12 的评测点，不要为了"看起来整洁"把它们都删掉。

### 5.5 只有标题没有正文

- 只有标题 + 空正文 → `reject` / `junk`，理由"空壳，无可复用内容"。
- 标题即一条完整知识点且能独立理解（如"HTTP 幂等：GET/PUT/DELETE 幂等，POST 不幂等"）→ `accept`，`note_type = concept`。
- 标题 + 一串链接/引用但无正文 → `reference` / `partial`（若链接本身构成索引价值），否则 `reject`。
- 标题 + 待办清单（有具体动作）→ `accept` / `normal`，`note_type = procedure`。
- 判据仍是三问；**不要**因为"以后可能会补"而给 `accept`。

### 5.6 表格为主的文件

- 表格**承载知识**（用例表、参数对照、缺陷清单）→ `accept` / `core`。
- 表格**承载业务数据**（考勤表、成绩单、报销单、签到表）→ 与 charter 无关，`reject` / `junk`；若与项目过程度量相关（缺陷趋势、工时统计）→ `accept` / `reference`。
- 表格 + 说明文字混排 → 以"说明文字是否给出结论"为主判据。
- 解析错位（合并单元格串列、表头错行）**不是**拒绝理由，只在 `human_reason` 记一句"表格结构有错位"，供后续解析器改进。
- 纯表格但只有表头没有数据 → `reject` / `junk`。

## 6. 标注者自一致性检查

**方法**（每个标注批次结束时执行一次）：

1. 从已标注样本中按 `seed = 42` 随机抽 **10 条**（记录抽中的 `rel_path`）；
2. **隔至少 3 天**，隐藏原标注，重新标这 10 条；
3. 比对 `human_verdict` 与 `human_quality`：

| 指标 | 阈值 | 不达标怎么办 |
|---|---|---|
| 判定（verdict）一致率 | ≥ 80%（8/10） | 改 rubric，不改直觉 |
| 质量（quality）一致率 | ≥ 70%（7/10） | 同上 |
| `partial` 相关的分歧条数 | ≤ 1 | 同上，重点补 §2.1 的 partial 判据 |

4. 每条分歧都要写下"当时两种想法分别是什么、卡在 rubric 哪一句"，然后：
   - **优先改 rubric 的判据文字**（加一条可执行的问句 / 反例 / 边界规则）；
   - 只有在确认 rubric 已明确、是自己没遵守时，才保留原标注；
   - **不要**用"这次凭感觉改一下"来消除分歧 —— 那是把噪声写进 ground truth。

5. 每次改动都在 §9 记一行，并注明改的是哪一节、为什么。

> 自一致性检查的目的不是"证明标得对"，而是**找出 rubric 里还没写清的地方**。

## 7. `labels.csv` 字段填写规范

按这个顺序填，前一步定了再填下一步（避免互相拉扯）：

| 列 | 填写规则 |
|---|---|
| `rel_path` / `filename` / `ext` / `char_count` / `split` | 脚本预填，**不要改**（`split` 若确有必要可改，改了就记在 §9） |
| `slot` | 填 1–14 的主槽位；随机抽样 / 不属任何槽 → 留空 |
| `human_verdict` | 只能是 `accept` / `partial` / `reject` |
| `human_quality` | 只能是 `core` / `normal` / `reference` / `junk` |
| `human_note_type` | `concept`（概念解释）/ `procedure`（步骤怎么做）/ `case`（案例、复盘）/ `reference_data`（查阅型资料）/ `log`（日志堆栈）/ `chat`（对话）/ `ad`（广告、单据、无关资料）/ `other` |
| `human_value_score` | 1–5 整数，锚点见下 |
| `human_is_partial` | `partial` → `true`；`accept` / `reject` → `false` |
| `human_reason` | **一句话必填**，模板"因为〔观察到的事实〕，所以判〔判定〕"。禁止"质量低""没用"这类空话 |
| `human_valued_span` | 仅 `partial` 必填：PDF 写 `p3-p5`，md/txt 写 `L40-L90`，docx 写 `段落 12-18`；其余留空 |
| `human_next_action` | `index` / `extract_spans` / `topic_dialog` / `drop` 四选一，规则见 §7.1 |

`human_value_score` 锚点：

| 分 | 含义 |
|---|---|
| 5 | 可以直接当作答案来源，几乎不用整理 |
| 4 | 稍加整理即可复用（补一句上下文） |
| 3 | 有信息，但要摘录/重组才能用 |
| 2 | 碎片，需要大量外部上下文 |
| 1 | 无可用信息 |

一致性自检（填完一批后跑一眼）：
- `partial` ⇒ `human_is_partial = true` 且 `human_valued_span` 非空；反之为错行；
- `reject` ⇒ `human_value_score` 应为 1–2；
- `accept` ⇒ `human_value_score ≥ 3`；
- `accept` ⇒ `human_next_action = index`；
- `partial` ⇒ `human_next_action = extract_spans`；
- `reject` ⇒ `human_next_action ∈ {topic_dialog, drop}`。

### 7.1 `human_next_action`：判定与动作是两件事

**「这份文件算不算笔记」和「接下来拿它干什么」是两个维度，必须分开填。**

| 值 | 含义 | 系统后续 | 对应判定 |
|---|---|---|---|
| `index` | 整篇就是笔记 | 切块 → 向量化 → 入索引 | `accept` |
| `extract_spans` | 文件里有**能直接用**的片段 | 只抽那几段入索引 | `partial` |
| `topic_dialog` | 整篇不能直接用，但**能引出值得学的话题** | 提取话题 → 和用户讨论 → 生成草稿 → 用户确认后入库 | `reject` |
| `drop` | 读完全篇没有任何可展开的东西 | 直接丢，**不浪费对话** | `reject` |

**`reject` 时必须再问一句**：这份文件里有没有一个"值得展开聊聊"的东西？

- **有** → `topic_dialog`。例：《项目实施记录（一）.md》当笔记看零价值，但含「Git 分支模型」「OCR 依赖链」等可展开话题。
- **没有** → `drop`。例：`hello.txt`、空文件、一段无上下文的 Traceback、一张壁纸。

判据：**能不能从这份文件里起一个"为什么/怎么做"的讨论？** 能 → `topic_dialog`；只能得出"这是什么" → `drop`。

> ⚠️ 为什么这列重要：`drop` 和 `topic_dialog` 都判 `reject`，但**后果完全不同**——
> 前者是正确地扔掉，后者是把一次再生机会扔了。`TASK.md` 的「误丢率」就是专门测这个的。

## 8. 明确不做的事（给后续阶段）

- 不在 rubric 里写任何"阈值"（字符数 ≥ N 就算好）—— 阈值属于 G1 的实现，不属于标注口径。
- 不给槽位之外的样本编造判定；没有真实文件就留空并写 `NA`。
- 不因为"想让指标好看"而调整某个文件的标注。
