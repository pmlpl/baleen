### 2.2 ⚠️ 判据精细化（待主人复核的设计决定）

首跑（run3）严格按旧判据「任何库内引用即 FAIL」判 6 FAIL——**逐条复核后发现 8 条全是同一形态**：

> 答案开头明示「笔记库里只有 X（背景）……所以下面的答案内容来自联网 [W1][W2]」；**答案主体全部标 [W n]**；[n] 只挂在「笔记里确实有的背景」句子上（如你的发票 OCR 笔记被 b01/b05 引作旁证）。

这是**诚实归因**，不是 11-18 方案 A 禁的「用自身知识补全答案再挂 [n] 引用背书」（那是拿 [n] 给答案内容背书）。旧判据是决策树时代定的——那时 web 答案（answer_web）天然不产库内引用，混合形态不存在。故 agent 档判据细化为：

- **FAIL = 库内引用 且 未联网**（真混合作答，两档同判；抓瞎引能力不减）
- 已联网（used_web）时背景真归因记 PASS，**answer_head/会话原文留档供人工抽查**（本批 8 条我已逐条复核，含 n01/b02/b05 全文）
- 决策树档不受影响（web 答案天然无库内 [n]，新分支不可达）

报告与脚本同时保留**严格口径读数**（见 `negative_report.md` 判据注记：本批严格口径 6 条会改判）。主人若不认可，回退只改 negative_eval.py 一个 if 分支；若认可「背景不挂徽章只文字提及」，则改 AGENT_ADDENDUM 一条规则即可（两个方向都已验证可行）。

### 2.3 动机案例 n02 实走（设计目标的直接证据）

模型行为：初始 `<context>` 只有 Google 论文起源段 → **换词再搜**（search_kb「Hadoop 生态 组件」）→ 仍无组件清单 → **转联网**（search_web）→ 答案开头「笔记库中只有关于 Hadoop 的**背景介绍**：GFS、MapReduce 的那些原则……所以下面的组件清单来自联网 [W…]」+ 背景句真归因 [4279]。

这正是任务书要交给脑的判断力：`_has_relevant_hit` 判「沾边」就混合作答的字面缺陷（本地档 n02 至今 gate=True 被饵中），agent 用两次工具调用+一次判断走对了。**决策树档对 n02 靠 4.5 前置闸把 web 结果先抓到手，agent 档靠脑在 loop 里判断后自己转网——同一条负例，两条路都 PASS。**

## 3. 每答 LLM 调用次数 / 时延 / 缓存（新指标）

### 3.1 调用次数分布（negative 8 条，agent 档）

- 决策树档：每答 1 次（web 路径）～2 次（[NO_KB] 二段路径）+ 追问改写 1 次（不进 agent 计数）
- **agent 档：8/8 条均为 2 次**（search_kb×N → 答案）；工具分布：search_kb 1–2 次/答、search_web 1 次/答（b04 用了 search_web×2）
- MAX_STEPS=6 硬上限 + 总预算 120s + 每步 45s（超了回落决策树；**本批零回落**，run4 无 trace=null 的答案）

### 3.2 时延（8 条/批，端到端含改写/检索/Tavily）

- run1 决策树档：P50 = 22.6s，max = 28.8s（当日首批，含 bge 冷启动 + 服务端缓存冷）
- run4 agent 档：**P50 = 12.3s，max = 13.2s**（9.2–13.2s 全距）
- 读数注意：两档非同刻跑，服务端负载与缓存状态不同；同日探针（3.3）里 agent 档 3 轮 3.6/6.6/5.2s vs 决策树档 3.4/5.5/6.0s——**同量级，agent 未引入时延劣化**。

### 3.3 前缀缓存（「工具结果断前缀缓存」的代价 = 不断）

**多轮探针**（同一组 3 轮追问、各开新会话、开关脚本自动翻转恢复）：

| 轮次 | agent 关 hit/miss | agent 开 hit/miss |
|---|---|---|
| turn1 | 640/1740 | 1280/1781 |
| turn2 | 2304/1797 | 2944/1818 |
| turn3 | 4096/1831 | 4736/1806 |
| **Σ** | **7040/12408 = 56.7%** | **8960/14365 = 62.4%** |

- **逐轮 hit 照常累积**（turn2 含 turn1 前缀、turn3 含 turn2）——append-only 设计生效，**`tools` 字段不打断 DeepSeek 前缀缓存**；
- agent 档反而略高（首轮起 system 前缀已在服务端暖 + 两档同 miss 形态 ≈ 每轮固定 ~1.8k 新 token）；
- 负例共 8 问同会话的批次读数：run1 决策树 59.8% vs run4 agent 76.6%——**有跨会话共享前缀（system）暖缓存的顺序混杂**（agent 批在后跑），以 3.3 探针（同刻对照）为准。
- 结论：ADR 0010 §6 的悬念落定——**前缀缓存不断，agent 的缓存形态与现状同构**。
