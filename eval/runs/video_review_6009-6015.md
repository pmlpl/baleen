## 二、三条通病的根因（主人总结 1/2 全中）

### 通病① 排版层级全拍平（代码纯文本 / 列表无标记 / 粗体丢失）

数据层是好的：6009 有 17 个 codeBlock、6013 有 bulletList、6012/6013 有粗体 marks。断在**展示链路复用了检索的纯文本序列化**：

```
doc(结构完好) → chunker._block_text(纯文本,检索上下文设计) → chunks 表
             → GET /api/notes → section.ts renderSectionText(启发式猜结构) → HTML
```

- [chunker.py:78-95](../../backend/app/service/chunk/chunker.py)：codeBlock 不带围栏（83-84）、bulletList 列表项不带标记（89-90）、粗体只取 text 节点 marks 全丢（81-82）
- [section.ts:260-271](../../frontend/src/utils/section.ts)：`looksLikeCode` 启发式只认 JS/Python 形态，bash/docker 命令全被当段落；无围栏/列表/粗体的对应渲染
- 实测：6009 的 39 个 chunk 含 ``` 围栏=0；6012/6013/6015 父块含 `**`=0、含列表标记=0

### 通病② 无用帧混入——筛选判「信息密度」不判「知识相关性」

- [_FRAME_TRANSCRIBE_PROMPT](../../backend/app/service/video_extractor.py:496)：INFO=high 的定义是「画面有实质可读内容——代码、幻灯片要点、软件界面」，搜索框/互动页**是**可读软件界面 → high
- [video_extractor.py:562-565](../../backend/app/service/video_extractor.py)：丢弃条件是「low **且**无 text_layer」——主播口播帧自带字幕文本，INFO 判 low 也照样保留；而字幕内容 whisper 早已转写，保留零增益
- 视觉模型其实「知道」这些帧没价值（6009 片尾帧描述：「视频结尾的互动引导画面，非技术内容」）——但这个判断没有被任何规则消费

### 通病③ 帧时机错位（6011 豆包淡帧 / 6012 NestJS 错位帧）

- [video_extractor.py:437-438](../../backend/app/service/video_extractor.py)：每场景**只在中点抽 1 帧**。动画过渡场景的中点落在淡入淡出过程上，截出来就是「内容很淡」的半成品帧

## 四、意外发现：arq 重投递已完成的导入任务

昨晚 23:06/23:10 完成的 6014/6015，今晨 11:26-11:55 被 worker **整套重跑**（重新下载+whisper+识帧，约 29 分钟），jobs 2971/2972 的 updated_at 变成今天 11:43/11:55：

- **笔记无损**：7 条笔记 created=updated 都是昨晚；今天 0 新笔记、0 新 media、sources 全部 parse_status=ok——pipeline 层 dedupe 挡住了产物覆盖
- **但有实害**：白烧 29 分钟算力+视觉 token（今晨视觉网关恰好挂了——识图智能体同款报错——帧全失败，否则又是一轮视觉调用费用）；6014/6015 的 video_log 被第二轮日志污染；6014 的 `video_frame_count` 键从 parse_meta 消失（重跑日志改写时首跑从未写入过该键——因为首跑零帧无 sidecar，两件事叠加成谜现已拆开）
- **根因**：worker 入口没有「source 已 parse_status=ok + 笔记存在 → 直接标 done」的幂等守卫；arq 对非正常关机残留 in-progress 状态的 job 重启即重投递（精确触发机制未钉死，守卫可以整类杀死）
- **旁证**：昨夜 6013/6014、今晨 6014/6015 的处理时间窗都重叠——实际是并发处理（此前「max_jobs=1 串行」的假设不成立）
