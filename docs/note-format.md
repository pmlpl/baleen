# baleen 笔记格式规范（note-format）

> **像接口契约一样严谨。** 人和 AI 在写笔记前必须读完这份文件。
> 不合规的笔记不会被静默丢弃——AI 会先修正；只有结构层硬约束修不了的，才标记人工复核。
>
> 本规范是**完整笔记契约**：格式层（§2–4，结构怎么写）+ 内容层（§5，什么是一篇好笔记）。
> 收敛了此前散落在多处的隐含要求，不推翻任何已锁定决策：
> `parse/blocks.py`（块类型）· `rewrite/outline.py`（标题规则）· `gate/g1.py`（价值信号）· ADR 0004（切块友好）· charter 判据 + Zettelkasten（内容层）。

---

## 0. 为什么要有这份规范

一个痛点，三个收益：

1. **闸门易过** —— 格式合规的笔记天然满足 G1 的结构信号、rewrite 的标题规则、切块的 heading 依赖，不用事后补救。
2. **RAG 友好** —— 从源头保证笔记能被正确切块（有标题、表格有表头、代码带语言、图片有 alt），避免碎片化和向量污染。
3. **人机一致** —— 不管人手写、文档导入、还是 AI 生成（未来的视频导出），产出都遵循同一份契约，AI 修正有据可依。

也顺带解决一个现实问题：**测试笔记没处找**。规范定下后，视频导出按规范产出，天然合规、可直接入库当语料。

---

## 1. 一篇笔记的组成

| 部分 | 说明 | 落在哪 |
|---|---|---|
| `title` | 笔记标题，**单独字段，不写进正文** | `notes.title` |
| `doc` | 正文；block JSON 是真源，markdown 是人/AI 的输入输出格式 | `notes.doc` |
| 元信息 | 来源类型、日期；视频笔记有额外字段（§6） | `sources` 表 + 待定字段 |

> 人和 AI 写笔记时，产出的就是 **一个标题 + 一段 markdown 正文**。系统负责转 block JSON、加编号、切块、向量化。
> 正文里不要重复标题；正文从第一个章节标题（`一、`级）开始。

---

## 2. 标题层级 【硬约束】

| # | 约束 | 为什么 |
|---|---|---|
| H1 | **必须有至少一个标题** | 无标题 → 切块退化成「整篇一个父块」、G1 零结构罚 0.4 分 |
| H2 | **只写语义标题，不写编号** | 编号由系统统一加（`一、` / `2.1` / `2.1.3`）；人写了易和系统编号不一致 |
| H3 | 层级 1=章 2=节 3=小节，建议不超过 4 级 | 层级过深会让检索溯源的 heading_path 很长 |
| H4 | **同级标题不重名** | 同级重名让 heading_path 歧义；rewrite 会判定需整理 |
| H5 | **标题后必须有正文或子标题**（不空壳） | 空壳标题切块产出空块，污染索引 |

**编号规则**（系统自动，人/AI 不写）：
- 一级：`一、` `二、` `三、`…
- 二级起：`2.1` `2.1.3`（进入更深层级时重置子计数器，保证 `2.1 → 2.1.1 → 2.2` 正确）

## 3. 块类型约定

支持的块类型（与 TipTap 兼容 block JSON 对齐）：

| 块 | 写法 | 约束 |
|---|---|---|
| 段落 `paragraph` | 基本单位 | 无 |
| 标题 `heading` | 见 §2 | 【硬】§2 全部 |
| 代码块 `codeBlock` | ` ```lang ` | 【硬】必须带 `language`；上下文注释（`# 文件:xxx > 函数:yyy`）由切块器自动加，人不用写 |
| 表格 `table` | markdown 表格，**首行表头** | 【硬】必须有表头行（切块会重复表头，没表头行脱离上下文无意义）|
| 图片 `image` | `![alt](...)` | 【硬】必须有 `alt`；【软】紧跟一段说明文字 |
| 列表 `bulletList`/`orderedList` | `- ` / `1. ` | 无 |
| 引用 `blockquote` | `> ` | 无 |
| 分割线 `horizontalRule` | `---` | 【软】前后留文字锚点 |
| mermaid / svg | ` ```mermaid ` / ` ```svg ` | 【软】前后留文字锚点（图脱离上下文，检索命中也看不懂）|

## 4. RAG 友好约束 【软约束：减分不拒】

| # | 约束 | 为什么是软的 |
|---|---|---|
| R1 | 每节正文 **250–2000 字** 理想 | 字数是内容属性，AI 改不了；短笔记按 charter「该收就收、标低质量」 |
| R2 | 不大量短行标题碎片（目录页式） | 污染向量索引（ADR 0004 §4.5 已识别并处理） |
| R3 | 孤立的代码/表格/图片，前后配一段文字 | 孤立块单独成 chunk 时文本量低、语义弱 |

> **为什么字数是软约束、结构是硬约束**：结构（标题/表头/alt/language）AI 能修正——补标题、补表头、补 alt 都是已实现或可实现的能力；字数是内容本身的属性，AI 不该为凑字数注水，也不该因笔记短就拒。这保住了 charter 的铁律：**误拒代价 ≫ 误收代价**。

---

## 5. 内容层：什么是一篇好笔记 【通用骨架】

格式层（§2–4）管「结构怎么写」，内容层管「写什么才算好笔记」。下面 5 条是**通用骨架**——不因人而异，任何用户的知识库都适用。个性化的「我具体收什么领域、什么形态」由 charter（问卷生成、存 DB）补充；G2 用 charter 判断，charter 生成时参考本骨架（见 `generator.py`）。

| # | 骨架 | 为什么 | 反例 |
|---|---|---|---|
| C1 | **用自己的话写，不摘抄** | 摘抄的内容网上能搜到，知识库的价值在「你想通的部分」；= charter 判据 + Zettelkasten「用自己的话」 | 把官方文档一段一段原样贴进来；课件 PPT 文字照抄 |
| C2 | **一节讲透一个要点**（原子化） | 一个小节 = 一个检索单元（切块），混在一起命中后看不懂；Zettelkasten 原子化。**项目的原子是小节，不是整篇**——一篇笔记可多节 | 一节里塞三个不相关概念；一段话讲完五步没展开 |
| C3 | **概念给定义 + 可运行例子**（+反例更好） | 只有定义没例子，检索命中也用不上 | 只写「闭包是函数和词法环境的组合」，无可运行示例 |
| C4 | **问题记录三段齐全且可复现** | 现象—原因—解决 + 版本/输入/触发条件；只有报错堆栈无上下文 → 命中也复现不了 | 只贴一段 Traceback，没说版本、输入、最后怎么解决 |
| C5 | **二手材料带出处，自己的理解和二手分开** | 区分「别人说的」和「我想通的」；Zettelkasten 文献笔记 vs 永久笔记 | 课件内容和自己的笔记混在一起，分不清哪是老师哪是自己 |

> **内容层与 charter 的分工**：本节是通用骨架（所有人都遵循）；charter（问卷生成、存 DB）是个性化判断（这个用户具体收什么、什么质量标准）。G2 用 charter，但 charter 生成参考本骨架——「好笔记」既有通用标准，又因人而异。
>
> **内容层不是闸门硬约束**：C1–C5 不像 §2/§3 那样能机械修正（「用自己的话」无法自动判定）。它们是写作准则，靠：① charter 生成 prompt 注入；② AI 生成笔记（视频导出）时遵循；③ G2 按 charter 判「有没有可复用知识」时参考。违反内容层不会自动拒。

## 6. 元信息约定

**通用**：
- `source_type`：`video` / `doc` / `web` / `manual`
- 日期：导入/创建时间（系统记录）

**视频笔记额外**（为未来的视频导出预留，存储待定）：
- `platform`：`bilibili` / `douyin` / …
- `url`：原始分享链接
- `author`：UP主 / 创作者
- `duration`：时长
- `chapters`：`[{title, start}]` 章节时间戳（若平台提供）

> 元信息的存储实现（复用 `sources` 表还是加 `metadata` 列）等做视频导出时定；本规范只约定「该有哪些字段」。

## 7. 不合规怎么办（修正机制）

| 场景 | 机制 |
|---|---|
| 文档导入 | rewrite 已做标题整理；**扩展成「格式归一化」**：补标题 + 校验块类型 + 补表头 / alt / language |
| AI 生成（视频导出等） | prompt 内嵌本规范，产出天生合规 |
| 手写 | 编辑器校验提示（未来 WYSIWYG 编辑器） |
| G1 闸门 | 格式信号纳入减分（已有零结构罚 0.4） |

**强契约执行点**：导入流水线在 rewrite 之后加一道格式校验。
- 硬约束（§2、§3 的【硬】）不合规 → AI 修正 → 仍不合规 → **标记人工复核**，不自动拒
- 软约束（§4）不达标 → 减质量分，照常入库

> 为什么「修正失败」是人工复核而不是自动拒：自动拒是 hard-to-reverse——你根本不知道自己丢了什么。charter 的铁律是「拿不准就收下、标低质量」。结构层硬约束真正修不了的极少（能补的 AI 都补了）；真修不了的，往往 charter 本身也该拒（纯报错堆栈、空壳文档）。给人工复核这道兜底，既严谨又不丢好内容。

## 8. 正例 / 反例

✅ **正例**（标题「闭包的形成条件」单独提供，正文如下）：

```markdown
## 一、什么是闭包

闭包是……（定义 + 可运行示例）

## 二、形成条件

### 2.1 函数嵌套

……

### 2.2 内层函数引用外层变量

……

​```python
def outer():
    x = 10
    def inner():
        return x
    return inner
​```
```

> 注意：正文里的 `2.1` `2.2` 编号是系统加的，人写时只写「函数嵌套」「内层函数引用外层变量」。

❌ **反例**：

| 反例 | 违反 | 处理 |
|---|---|---|
| 一整段长文没有标题 | H1 | rewrite 补标题 |
| 标题写成 `## 2.1 闭包`（带编号） | H2 | 系统统一加编号，人写的会不一致 |
| `## 错误处理` 出现两次（同级重名） | H4 | rewrite 重命名区分 |
| `## 进阶用法` 下面直接是下一个 `##` 标题，无正文 | H5 | rewrite 补子标题或合并 |
| 表格没有表头行 | §3 表格【硬】 | AI 补表头 / 标记复核 |
| `![](x.png)` 没有 alt | §3 图片【硬】 | AI 补 alt |
| ` ``` ` 代码块没有 language | §3 代码【硬】 | AI 推断 language |
| 一篇只有目录式短行的笔记 | R2 | 软约束，减分不拒 |
