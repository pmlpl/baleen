# ADR 0004：文本切块规则

- **日期**：2026-10-28
- **状态**：已采纳（参数待实验校准，见 §8）
- **关联**：ADR 0001 决策 3/4、ADR 0003 的 `chunks` / `embeddings` 表

---

## 1. 背景与两条硬约束

`bge-large-zh-v1.5` 的 `max_seq_length = 512`，vocab 21128 → **约 1 汉字 ≈ 1 token**。

由此得到**第一条硬约束**：

> **送进 embedding 的文本必须 ≤ 512 token**。超了会被 tokenizer **静默截断**——不报错、不警告，
> 只是最后 100 字直接消失。检索掉点且极难排查。

**第二条**：`embeddings` 表只有**子块**有行（ADR 0003 决策 ①）。父块不参与向量化。

> ⚠️ **诚实标注**：下面 §3 的具体数字（300 字、250–400 区间）**是从 512 上限推导的安全边际，
> 不是实验结论**。真正该用多大，要靠 §8 的消融实验来定。当前实现先按这个值，并把它写成常量。

---

## 2. 三层结构

```
note（一篇笔记，block JSON）
  │
  ├─ ① 按 heading 结构切
  ▼
section = 父块（一个完整小节，800–5000 字不等）
  │                     ← ★ 不 embed，只在库里当上下文
  │
  ├─ ② 按语义/长度切
  ▼
chunk = 子块（250–400 字）
                        ← ★ 只有它进 embeddings
```

**检索时**：子块命中 → 反查 `parent_id` → **整节喂给 LLM**。

一句话：**小块负责"找得准"，大块负责"答得全"**。
子块单独拿出来常常看不懂（"它"指谁？），而整篇塞进向量又会让语义被稀释。

---

## 3. 参数（★ 待实验校准）

| 参数 | 当前值 | 说明 |
|---|---|---|
| `TARGET_CHARS` | **300** | 子块目标汉字数 |
| `MIN_CHARS` | **250** | 低于此值优先并到相邻块（除非是独立表格/代码） |
| `MAX_CHARS` | **400** | 硬上限。**任何子块超过 400 必须再切** |
| `HARD_TOKEN_LIMIT` | **480** | 用 bge tokenizer 实测 token 数；超了强制再切（留 32 token 余量） |
| `OVERLAP` | **0** | **不做重叠**。见下方理由 |

**为什么 `OVERLAP = 0`**：

重叠切块是为了防"跨块语义被切断"。但本项目**父块会整节喂给 LLM**——即命中任意一个子块，
模型看到的是完整小节，跨块断裂的问题天然被 small-to-big 消化掉了。
再加重叠只会让存储翻倍、召回结果重复。

**唯一例外**：句子**绝不劈开**。累积到超限时，在**最近的分句边界**（`。！？；\n`）断开。
一个句子本身超过 400 字（罕见）→ 给一个 `warning` 并整句保留（宁可超长也不毁语义）。

## 4. 切块算法

### 4.1 主流程（流式，单遍）

```
输入：note.doc（block 数组）
输出：sections[]，每个含 chunks[]

state:
  heading_path = []      # 当前标题栈，如 ["三、闭包的坑", "3.1 内存泄漏"]
  cur_section  = None
  cur_chunk_blocks = []
  cur_chars = 0

for block in note.doc.content:
    if block.type == 'heading':
        ① flush 当前子块；② flush 当前父块（除非父块还空）
        ③ 按 level 维护 heading_path（同级替换，低级清空）
        ④ 开新父块，heading_path 快照
        ⑤ heading 本身也塞进父块（作为父块开头的小标题上下文）
        continue

    if block.type == 'table':
        flush 当前子块
        push_table(block)        # 见 4.2，表格按行切
        continue

    if block.type == 'codeBlock':
        flush 当前子块
        push_code(block)         # 见 4.3，代码按函数切
        continue

    # 普通段落 / 列表
    塞进 cur_chunk_blocks
    cur_chars += 该块文本字数
    if cur_chars >= TARGET_CHARS:
        flush 当前子块

末尾：flush 子块 → flush 父块
```

### 4.2 表格：按行切，**每块重复表头**

```
原始 50 行表格
  → 子块 1: 「参数表(1/3)｜表头：名称|类型|默认值」+ 前 18 行
  → 子块 2: 「参数表(2/3)｜表头：名称|类型|默认值」+ 第 19-36 行
  → 子块 3: 「参数表(3/3)｜表头：名称|类型|默认值」+ 第 37-50 行
```

**为什么要重复表头**：表格行脱离表头就没有意义（"5 | 是 | 3" 是什么？）。
重复表头会多占几十字，但换来"任意一行都能被正确理解"。

小表格（总字数 ≤ `MAX_CHARS`）→ **整张表一个子块**，不切。

### 4.3 代码块：按函数/类边界切

```
优先级：函数/类边界 > 空行分组 > 行
每块开头附一行 context：`# 文件: xxx.py > 函数: parse_pdf()`
```

**为什么**：切在函数中间会让"这段代码在干什么"失效。
代码块**不受 `MAX_CHARS` 严格约束**（`HARD_TOKEN_LIMIT` 仍生效）——一个 600 字的完整函数，宁可超长也不切开。

### 4.4 无 heading 的长文

没有标题锚点 → 整个笔记就是**一个父块**，子块按句子边界累积到 300 字。
`heading_path` 为 `None`，检索时只回退到"整篇"这一级上下文。

### 4.5 目录页：识别并**单独成块，不 embed**

**识别特征**（命中 ≥2 条）：
- 大量形如"第X章"、"1.2.3"、"……数字"的行
- 行平均长度 < 20 字
- 短行占比 > 60%

**处理**：单独成一个子块，`meta.skipped_embed = true` → **不写 `embeddings` 行**。

**为什么不等价于丢弃**：目录是很好的导航信息，留着能让"这篇笔记讲了什么"被回答；
但它的内容全是标题碎片，embed 进向量会是纯噪声（问"内存泄漏"命中目录页会选错）。

### 4.6 图片块

一整个 `image` 块 → 单独一个子块，文本为 `"[图片] alt 文本"`。
如果后面紧跟一段文字说明，**并进同一个子块**（图和它的说明是一体的）。

OCR 未接入前，图片子块**文本量极低** → 也不 embed（避免"空块"污染索引）。

## 5. `heading_path` 与溯源

每个子块都存 `heading_path`，形如：

```
三、闭包的坑 > 3.1 内存泄漏
```

**用途**：
1. **引用**：回答里说"出自《闭包的坑》第 3.1 节"
2. **检索上下文**：把 `heading_path` 拼进 embed 的文本前部，能显著提升"这个块属于哪个主题"的判别力

**拼接格式**（喂给 embedding 的最终文本）：

```
{笔记标题} > {heading_path}
{子块正文}
```

> 父块的 `heading_path` 是它自己的标题；子块的 `heading_path` 是完整面包屑。

## 6. 硬指标（验收卡尺）

每次切块后必须能报出这四个数：

| 指标 | 要求 |
|---|---|
| `chunks_total` | — |
| **`chunks_over_limit`**（token > 480） | **必须 = 0** |
| **`chunks_truncated`**（被 tokenizer 截断） | **必须 = 0** |
| `chunks_in_range`（250 ≤ chars ≤ 400 的占比） | 目标 ≥ 70%，低于 60% 要给 warning |

> **`chunks_truncated` 必须由程序自己算**：调 `tokenizer(text, truncation=False)` 数真实 token，
> 不能靠字数估算。这是唯一能保证"没被静默截断"的办法。

---

## 7. 明确不做

| 不做 | 理由 |
|---|---|
| 语义切块（用 embedding 找断点） | 要跑两遍模型，慢且贵；结构化笔记靠 heading 就够 |
| 滑动窗口重叠 | 见 §3，父块已经解决了上下文断裂 |
| 递归切分到固定 token 数 | 会破坏表格和代码结构 |
| 按页切 PDF | 页边界和语义边界无关 |
| 给父块也 embed | 违反 ADR 0003 决策 ①，会让 512 变成真瓶颈 |

## 8. 参数校准方法（未来要做的实验）

**现状**：§3 的参数是推导的，不是测出来的。**这是本文档最大的已知弱点。**

**实验设计**（前置依赖：20 个 query 集）：

```
固定：同一批 20-30 篇笔记、同一个 embedding 模型、同一套检索与 rerank
变量：TARGET_CHARS ∈ {200, 300, 400, 600}
指标：Recall@5 / MRR / nDCG@10
```

**判据**：如果 200 和 400 的 Recall@5 差异 < 3%，说明**这个参数不敏感**，维持 300 即可（省事）。
如果差异显著，取最优值并把本文档的参数改成实测值。

> 参考先例：同门 asklaw 做过"38 条人工标注问题 × 三种切分策略"的同类实验。
