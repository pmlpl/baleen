- **日期**：2026-10-28
- **状态**：已采纳（本 ADR 是全项目的地基，后续 ADR 都在它下面展开）

## 1. 背景与约束

**baleen** —— 中文优先的个人智能笔记库。定位一句话：

> 一个能自己判断该不该收、收了之后还能被追问出处的本地知识库。

**硬约束（这些约束决定了下面每一条决策）**：

| 约束 | 含义 |
|---|---|
| **本科毕业设计** | 一个人、有限时间、要能答辩演示 |
| **单用户** | 不做注册登录、多租户、计费 |
| **断网可演示** | 答辩现场可能没有网络、没有 API key |
| **中文为主** | 分词、检索、embedding 都按中文优化 |
| **可复现** | 同一输入跑两遍，结果必须一致 |

---

## 2. 决策清单

### 决策 1：PostgreSQL 单库承载「业务 + 向量 + 全文 + JSONB」

**为什么**：删一篇笔记要同时动 `notes` / `chunks` / `embeddings` / `review_runs` 四张表。在单库单事务里这是 4 行 SQL；一旦向量放到独立库，就变成跨系统的分布式一致性——**必然产生孤儿向量**。

**代价**：向量检索性能不如专用库；受 pgvector 能力限制（如维度写死，见 ADR 0003）。

**何时该推翻**：chunk 数 > 500 万，或需要按租户物理隔离索引。

---

### 决策 2：不引入独立向量库（Qdrant / Milvus）

**为什么**：按 1 万篇笔记 / 2.5 万块估算，1024 维 halfvec 约 50 MB，HNSW 索引几十 MB。**PG 连热身都算不上**。为一个用不到的量级引入一套运维，纯亏。

**代价**：换模型或换检索算法时灵活性差。

**何时该推翻**：同上，chunk > 500 万。

---

### 决策 3：笔记真源 = block JSON（TipTap 兼容），markdown 只是渲染

**为什么**：表格、图片、公式、代码块**需要结构**。markdown 存不下"合并单元格"，图片只能存路径，公式退化成字符串。
且 block JSON 就是 ProseMirror/TipTap 的文档模型——**将来加编辑器是纯加法，不用重构**。

**代价**：所有导出、展示、切块都要先理解 block 树；调试比看 markdown 麻烦。

**何时该推翻**：永远不该。这是本项目最不该动的一条。

---

### 决策 4：Embedding 用本地 `BAAI/bge-large-zh-v1.5`

**为什么**：**断网可演示是硬需求**——答辩现场不能依赖云端 API。而且免费、1 万篇全量索引 CPU 上 5–15 分钟。

**代价**：
- 只有 512 token 上下文 → **切块必须 ≤ 400 字**（详见 ADR 0004）
- 同门 asklaw 已做过实验：**本地 bge 在"条款精确检索"任务上不如云端 embedding-3**。baleen 接受这个先验，因为选它不是为效果，是为离线。
- 换更强的模型不是改配置，是**新建向量表重建**（见 ADR 0003 §4）

**何时该推翻**：如果做成了给别人用的产品（不再需要断网演示），或检索效果被证明是瓶颈。

---

### 决策 5：导入是**确定性状态机**，不是 agent loop

**为什么**：如果让 agent 自主决定"下一步做什么"，会有三个必然后果：
1. 同一个文件跑两次结果不同（不可复现）
2. 卡在中间不知道死在哪一步（不可排查）
3. 每一步都要花 LLM 的钱（不可控）

**必须能对着原始文件从头重放。**

**代价**：流程僵化，遇到没见过的格式只能报错，不能"智能变通"。

**何时该推翻**：永远不该。灵活性放在闸门的**判定逻辑**里，不放在流程控制里。

---

### 决策 6：审核拆三道闸（G0 解析 / G1 价值 / G2 归属）

| 闸门 | 判什么 | 手段 | 成本 |
|---|---|---|---|
| **G0** | 能不能读出东西 | 确定性规则 + 解析器 | ≈ 0 |
| **G1** | 有没有实质内容 | 启发式（字符数、结构信号、重复、样板词） | ≈ 0 |
| **G2** | 属不属于这个库、有没有可复用知识 | 一次文件级 LLM 调用 | 有 |

**为什么拆三道**：**便宜的先跑、早退**。真实使用中 80–90% 的垃圾在 G1 就能拦住，永远不进要花钱的 G2。

**代价**：三条规则要分别维护、分别评测。

**何时该推翻**：永远不该。

---

### 决策 7：G2 判定的是「有没有可复用知识」，**不是**「属于哪个学科」

**为什么**：领域分类永远列不全（"计算机 + 建筑"的 BIM 算什么？），而且换个人就失效。而"有没有可复用知识"是**有限集、可判、跨领域通用**。

判定落在三问上（见 `eval/rubric.md` §0）：
1. 有没有一句话，是作者以外的人能直接拿去用的？
2. 拿走作者记得的上下文，这段内容还站得住吗？
3. 换一台机器、换一个项目，它还能复现/复用吗？

**代价**：判"价值"比判"分类"主观，需要人工标注集来校准。

**何时该推翻**：永远不该。

---

### 决策 8：charter 是**每个知识库自己的一段自然语言**，不是枚举字段

**为什么**：`domain ENUM('computer','architecture','law',...)` 是给自己挖坑——领域无限长、填不全、跨领域直接崩。
charter 写成一段话（"收什么、不收什么、给谁用"），换个人换一段话即可，**代码一行不改**。

**硬规则**：代码里**永远不许出现**任何形式的领域分类枚举。

**代价**：charter 质量取决于用户（所以要提供自动归纳模板，见产品设计）。

---

### 决策 9：单用户 → 闸门策略是「**默认收 + 标质量**」，不是「默认拒」

**为什么**：
> **误拒的代价 ≫ 误收的代价。**
> 收错了，你随时能删；拒错了，**你根本不知道自己丢了什么**。

所以：`accept / partial / reject` 之外还要标 `core / normal / reference / junk`；`junk` 不进默认检索但留在库里可查；用户永远可以一键强制收下。

**代价**：库内容会变脏一些，靠质量分级而不是靠准入来控噪。

**何时该推翻**：如果做成多人共享库（别人扔垃圾的成本变成你的），策略要反过来。

---

### 决策 10：LLM 全部走 **OpenAI 兼容协议** + adapter 表

**为什么**：用户自带 key，且可自由选厂商。统一协议后，OpenAI / 智谱 / DeepSeek / Ollama / vLLM 都在同一套接口下。
需要额外维护的只是**能力标记**（JSON mode / vision / tool calling / 上下文长度），缺能力时降级。

**代价**：各家兼容性参差，需要一层适配与探测。

---

### 决策 11：embedding 记录 `model + dim`，换模型走「新建 + 重建 + 切换」

**为什么**：换 embedding 模型 = **全库向量作废**。原地覆盖没有退路；新旧并存才能灰度切换、才能回滚。

**代价**：多一张表、多一次 join（见 ADR 0003）。

---

### 决策 12：业务表预留 `owner_id`（单用户写死 1）

**为什么**：从"自己用"到"给别人用"的成本，几乎不在数据模型上，而在安全、分配、合规、支持上。
但**数据模型是唯一改起来最痛的部分**——现在加一个字段几乎零成本，以后加要动所有查询。

**配套硬规则**：所有查询走 `Repo(owner_id)` 薄封装，**不许裸用 session**；禁止模块级可变全局状态（`current_user` 一律靠参数传）。

**代价**：多一层薄封装，写起来多几行。

## 3. 被明确否决的备选方案

这一节比决策本身更重要——**答辩时最容易被问"为什么不用 XXX"**。

| 备选 | 否决理由 |
|---|---|
| **MongoDB 存笔记** | 笔记→版本→块→向量是四层树，丢掉关系完整性必然产生孤儿数据；混合检索（向量+全文）在 Mongo 里要手搓 |
| **独立向量库 Qdrant / Milvus** | 当前量级（2.5 万块）用不到；多一套运维和一套一致性 bug |
| **Elasticsearch / Meilisearch** | 中文召回不满意了再说；作为**旁路索引**可以，**绝不做真源** |
| **Markdown 作为真源** | 存不下表格合并单元格、图片、公式结构；且 block JSON 才能直接喂编辑器 |
| **云端 embedding API（如智谱 embedding-3）** | 断网无法演示；且引入 key 依赖。**但它和 bge 同为 1024 维，随时可切换** |
| **让 agent 自主驱动导入流程** | 不可复现、不可排查、成本不可控 |
| **领域枚举 / 下拉框** | 领域无限长、跨领域崩、换人就失效 |
| **提前做多用户 SaaS** | 毕设评分不看；会吃掉 15–20% 工期换 0 分 |
| **PaddleOCR 进主依赖做自动 OCR** | 722 MB + 三个 Windows 坑 + 26–113 秒/页，换来的只是 3/35 的样本；"检出即拦截"更划算 |
| **pdfplumber 作为 PDF 解析主库** | 裸文本流在窄列堆叠区会产生字符交错（对嵌入是毒药），且慢 20–40 倍（实测见 ADR 0002） |

---

## 4. 后果

**正面**：
- 数据模型简单，一个事务能处理绝大多数业务操作
- 断网可完整演示（解析、embedding、检索全本地）
- 每个决策都有可验证的推翻条件，不是信仰

**负面（必须承认）**：
- 检索质量受限于本地 bge，且**换模型的成本是"重建全库"而非"改配置"**
- 中文全文检索靠 `pg_trgm`（二元组），不如专业分词器
- 单用户假设一旦被打破，闸门策略和权限模型都要重做
